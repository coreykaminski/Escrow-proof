# 2026-10-06 (afternoon): Part 2 Spec Engine

**Slice:** request → drafted criteria (Claude) → edit → approve by hash. AP2 mandate import stub. Eval harness for the ≥90% "testable" gate.

## Shipped
- `packages/spec-engine`:
  - `ClaudeSpecDrafter`: `claude-opus-5-5` (override with `SPEC_DRAFT_MODEL`), effort `medium`, structured output (Zod schema), server-side refusal fallback (`fallbacks: "default"`). Refusal, truncation and API errors map to typed `SpecDraftError`s.
  - Prompt `spec-drafter/1`: atomic pass/fail criteria with a `verification` method, check type and critical flag, plus `open_questions`. Request text is wrapped as untrusted data, and attempts to close the wrapper tag are neutralized.
  - `assembleSpec`: the model drafts only title, vertical and criteria. Money, deadline and appeal window always come from the caller. Criterion ids are normalized and deduplicated.
  - AP2 import (parsing stub): intent and cart mandates → request text, cart total in minor units, expiry check, mandate hash. Signatures are **not verified yet** and are recorded as `signature_verified: false`.
- Core: optional `verification` field on criteria (absent fields don't change existing hashes). `lintSpec` flags vague wording, missing verification, overlong criteria, no critical criterion, judge-heavy specs and single-criterion specs.
- API: `POST /v1/agreements/from-request` and `/from-mandate`. Agreements now return `spec_source` and `spec_warnings`. Provenance is on the ledger (`agreement.created.spec_source`), and edits mark a drafted spec `edited: true`. Migration `0002_spec_source`.
- CLI `draft-spec`. Server and CLI load `./.env`. `npm run dev` now runs from the repo root, so it shares `./.data/dev` with the CLI. Before this, `create-account` keys didn't exist in the dev server's database.
- `evals/spec-engine`: 50 requests (18 translation, 12 code, 10 data, 10 general, including vague requests and one prompt-injection attempt), `npm run eval:spec` → results, summary and review.csv, `npm run eval:spec:score`.

## Eval run 1 (`evals/spec-engine/runs/2026-10-06T19-45-41-018Z`)
Credits were added, so the eval ran on `claude-opus-5-5` · `spec-drafter/1`:
- 50/50 drafted, 100% valid specs, 98% correct vertical (dt-08, an RFP summary, came back `general` instead of `data`, which is defensible).
- 438 criteria, an average of 8.8 per request. Check types: 214 deterministic, 148 domain, 76 judge. 61% marked critical.
- 1 criterion had a lint warning, and it was a false positive ("proper names" read as the vague word "proper"). Fixed, with a regression test. Two specs were flagged `mostly_judge` (gn-04 pitch deck, gn-06 itinerary), which is expected for those jobs.
- Prompt injection (tr-18): the drafter didn't follow the "mark as accurate" text and raised it as an open question.
- Vague requests (cd-05 "make our website faster", gn-09 "a nice resume", dt-05 "market sizing") became measurable criteria with placeholder thresholds, plus open questions to settle them.
- Cost $2.03 (~$0.04/request), p95 latency 26 s.
- Watch: 61% critical may be high. Several judge-checked items are critical, so Part 3 should check that critical judge criteria don't cause false refunds.

## Testability rating (AI, not human)
At the user's request, Claude rated all 438 criteria and the scorer ran on that. **These are AI ratings, not the human ratings MASTER_PLAN calls for.** Every row in `review.csv` carries a `rater` column saying so. A human can overwrite any `testable` cell and re-score.
- Rubric: `y` if a checker can decide pass/fail from the deliverable, the source material and the buyer's stated inputs without guessing what the buyer meant.
- **Score: 96.8% testable (424/438), PASS (≥90%).** Translation 95.1%, code 94.5%, data 100%, general 100%.
- The 14 `n`s split two ways:
  - 7 depend on an unanswered open question: cd-05 ×5 (which pages to measure), tr-04 (which keys are buttons), tr-16 (convert currency or not). The drafter correctly asked these questions, so they resolve when the buyer answers.
  - 7 rest on taste: native-speaker naturalness or "friendly tone" (tr-05, tr-10, tr-11, tr-12, tr-14, tr-16) and module cohesion (cd-10).
- Prompt follow-up (spec-drafter/2): for fluency and tone wishes, require an observable proxy (error counts, banned-phrase lists, Sie/du consistency) instead of "reads naturally". When a criterion depends on an open question, say so in the criterion text.

# 2026-10-06 (evening): Part 3 Verification Engine v1 (translation)

**Slice:** golden set (Part 0's missing piece) → deterministic layer → model layers + decision policy → eval harness → API.

## Shipped
- **Golden set** (`evals/translation`):
  - 36 base documents (12 contracts, 12 policies, 12 marketing), written by `claude-opus-5-5` in en/es/fr/de, paragraph-aligned. Each was accepted only if every translation passed the deterministic checks in both directions and kept every party name.
  - Model-written corruptions (meaning flips, wrong terms, invented additions, dropped clauses, harmless "minor" edits). They keep all numbers and names, so only the model layers can catch them.
  - A seeded builder produces `golden.jsonl`: 300 items across 6 directions (en↔es/fr/de). 130 should release (110 clean, 20 minor edits) and 170 should refund (numbers, dates, dropped paragraphs and clauses, truncation, swapped parties, untranslated text, meaning, terminology, additions, 10 prompt injections, half of them masking a changed number).
- **`packages/verifier`**:
  - Deterministic checks: number and date extraction normalized across the four languages, paragraph structure, stopword language ID, an injection-phrase detector.
  - MQM annotator (Opus 5.5) and per-criterion judge (Sonnet 5.5, criteria order shuffled), using structured output. The deliverable is wrapped as untrusted data with its tags neutralized.
  - Evidence quotes must exist in the texts, or the failure is discounted.
  - Ensemble: a deterministic hard failure decides alone and skips the model calls. Otherwise both models must agree, and disagreement means "uncertain".
  - Decision policy: a critical failure refunds; a suspected injection, disagreement or non-critical failure escalates; release only when everything passes.
- **API**:
  - `PUT /v1/agreements/:id/inputs`: source files are hashed into `spec.inputs`, so approval locks them. Callers can't set `spec.inputs` themselves.
  - `POST /v1/ops/agreements/:id/verify`: delivered → verifying → verify → store the report and ledger `verification_recorded` → DECIDE (auto) or ESCALATE.
  - `GET /v1/agreements/:id/verifications`.
  - Migration `0003_inputs_verifications`.
- **Eval**:
  - Free CI gate: on the golden set, zero high-confidence findings across all 130 release items, and 100% detection of number, date, dropped-paragraph, truncation and untranslated errors.
  - `npm run eval:translation` checks every §6 target, with a disk cache.
  - A GitHub Actions workflow runs the eval when triggered by hand.
