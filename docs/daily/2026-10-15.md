# 2026-10-15: Load testing, and the backup and restore drill

## 10. Load test
- **`npm run load-test`:** starts the real server on a real (embedded) Postgres and drives it over HTTP. Or point it at a deployment with `LOAD_TARGET_URL` and `LOAD_API_KEY`.
- **Four scenarios at concurrency 1, 8 and 32:** authenticated reads, full purchase flows (4 writes), Verify API checks, and public tree heads.
- **Baseline** (`docs/perf/load-test-2026-10-15.md`), with zero errors:
  - About 170 purchase flows per second, 60–70 checks per second, and 1,500–2,000 reads per second.
  - Roughly 250× headroom over a 100× burst at the plan's $1M ARR volume.
- **First bottleneck:** the global ledger lock (purchases plateau at 8 concurrent clients). Revisit near 100 sustained writes per second.

## 11. Backup and restore drill
- **`packages/db/backup.ts`, with `npm run db:backup` and `npm run db:restore`:**
  - Backups are logical: one consistent snapshot, every table in primary-key order (COPY text format), and a manifest of counts, sha256 per table, the migration level, the ledger head and the Merkle root. A broken ledger is refused.
  - Restore needs an *empty* database (`RESTORE_DATABASE_URL`, never `DATABASE_URL`). It migrates, loads in foreign-key order, then verifies every table byte for byte, the hash chain from genesis, head and root, and that the ledger is still append-only.
- **`npm run backup-drill`** (report: `docs/ops/backup-drill-2026-10-15.md`), passed. On embedded Postgres:
  - 40 settled jobs and an anchor; backup of 27 tables, about 1,500 rows, 357 KB, in 65 ms.
  - 10 more jobs and a second anchor after the backup.
  - Restore in 136 ms, every check passing.
  - The app on the restored database serves an offline proof that verifies against the first anchor.
  - The anchors check flags the second anchor ("the ledger is shorter than this anchor"). A rollback to an older backup can't go unnoticed.
- **Tests (real Postgres only; skipped on PGlite):** exact round trip with tabs, newlines and backslashes; a tampered backup fails the table checksum and the hash chain; restoring over existing data is refused.
- **Runbook:** a backups section. Neon point-in-time restore is primary, the daily logical copy goes off-site, plus post-restore anchor checks and a quarterly drill.
- **Needs a decision:** where the encrypted off-site copies are stored.
