# 2026-10-10: Deployment readiness (no credits needed)

## 1. Shared rate limits
- **Before:** counters were per process, so with two Fly web machines every limit was doubled and reset on each deploy.
- **Now:** `PostgresRateLimitStore` keeps the counters in Postgres. It's one atomic upsert per request, and a window restarts once the stored one has ended. The worker sweeps finished windows every 10 minutes.
- **Default:** the server uses it unless `RATE_LIMIT_STORE=memory`.
- **If the store fails:** the limiter lets the request through and logs it, so it can't take the API down.
- **Tests:** two app instances on one database share a single limit; windows reset; finished windows are swept; the limiter fails open. Migration `0012_rate_limits`.

## 2. Ledger proofs from stored subtrees
- **Before:** every proof, `/verdicts.json`, `/ledger/checkpoint.json` and `/ledger/consistency.json` re-read every ledger entry (O(n) per request, on public URLs).
- **Now:** complete Merkle subtrees are stored once in `ledger_tree_nodes`; in an append-only log they never change. Roots and proofs need O(log n) nodes, fetched in one query: `nodesNeeded` does a dry run to learn which nodes a computation reads.
- **Append cost:** each ledger append stores its leaf and the nodes it completes with one lookup and one insert, inside the same transaction and lock.
  - Measured: about +3% on the agreements and payments tests (22.2 s against 21.6 s).
  - The full suite's slower times today are machine load (load average around 28), not this change.
- **Backfill:** a ledger without stored nodes is rebuilt in order on first use, so stored leaves always form a gap-free prefix.
- **The cache can't decide what gets vouched for:** the daily anchor still recomputes the root from the entries and refuses to anchor if the stored nodes disagree (tested by corrupting a node). `verifyAnchors` uses only the entries.
- **Tests:** the stored-subtree functions match the leaf-by-leaf ones for every size up to 70; the cached root equals a full recompute at every ledger size; backfill and corruption are covered. Migration `0013_ledger_tree_nodes`.

## 3. Tests on real Postgres
- **`npm run test:postgres`** runs the whole suite on real Postgres.
  - Locally it uses an embedded Postgres from npm (`embedded-postgres`, dev dependency; no system install).
  - In CI it uses a `postgres:17` service container (new `postgres` job in `ci.yml`).
- **Setup:** one migrated template database per run. Each test harness gets its own clone (`createTestDb`), dropped on close.
- **Result:** all 702 tests pass on Postgres 18, the first time.
  - The concurrent-append test now also checks that the stored Merkle subtrees match a full recompute under real concurrency.
- **Default `npm test`** still uses in-process PGlite (fast).
- **Audit:** the only advisories are the same four moderate dev-only ones (drizzle-kit's esbuild).

## 4. Criteria templates
- **Four templates** (`packages/spec-engine/templates.ts`). Their criteria use the golden sets' ids and wording, so the verifiers route to them exactly as in the measured evals.
  - `code.acceptance-tests`: public tests, plus optional held-out `[hidden-tests]`.
  - `data.dataset`: schema, minimum records, unique key.
  - `research.cited-brief`: minimum sources, links load, verbatim quotes.
  - `translation.document`: values, omissions, additions, meaning, target language, plus optional register.
- **No model needed:** the code, data and research templates decide without any model call. Translation's meaning and register criteria need the model layers.
- **Where you can use them:**
  - `GET /v1/spec-templates` lists them, with params as JSON Schema.
  - `POST /v1/agreements/from-template` records `spec_source: {kind: "template", template, version}`.
  - The Verify API and A2A accept `template: {id, params}` in place of `spec`.
  - Also the SDK (`specTemplates.list`, `agreements.createFromTemplate`) and the MCP tool `verify_work`.
- **Tests:**
  - Every template builds a lint-clean spec.
  - Translation routing checked per error category. This added a critical "meaning preserved" criterion, without which model-found mistranslations would have had no criterion to fail.
  - End to end on the real verifiers: hidden tests catch a solution that only passes the public test; the CSV fails on count and on duplicates; the brief fails on too few sources and on a misquote.
- **Found while testing:** a quote in a paragraph that cites two sources can't be attributed, so it escalates by design. The research template now tells sellers to keep one source per quoted paragraph.

714 tests passing. Today's slow full-suite runs were machine load: macOS iCloud sync and Spotlight (load average up to 164), not the code. Each file passes in isolation.

## 5. Observability
- **Request ids:** every response carries `X-Request-Id`; a well-formed incoming one, such as Fly's, is kept. Error bodies include `request_id`.
- **Logs:**
  - One structured line per request: method, **route pattern** (never the concrete path, so share and payment tokens can't leak into logs), status, ms, account and key.
  - JSON in production, text locally. `LOG_LEVEL` and `LOG_FORMAT`.
  - The server and worker log through the same logger.
- **`GET /v1/ops/metrics`:**
  - This instance's request counts by status, latency p50/p95/p99, and the busiest routes.
  - Per-vertical checks, escalation rate, latency and model cost over 24 h.
  - The scheduler heartbeat.
- **Alerts:** `ALERT_WEBHOOK_URL` (Slack/Discord-compatible) on 500s, worker tick failures and a failed ledger check.
  - At most once per kind per 10 minutes. It never throws.
- **Tests:** ids kept or replaced; one log line per request with route patterns and no secrets; metrics after a real verification; one alert for two 500s; a webhook outage doesn't break anything.

718 tests passing (`--maxWorkers=3`; full-width runs time out while macOS indexing loads the machine).

## 6. Security scanning in CI
- **New `security.yml`** (on push, PRs and weekly):
  - CodeQL (`security-extended`) for the TypeScript.
  - gitleaks over the full history.
  - `npm audit --omit=dev` on production dependencies.
- **Pinned actions:** every GitHub Action is pinned to a commit SHA (version in a comment). Workflows run with read-only `contents` permissions.
- **Dependabot:** npm (production and dev grouped), actions and the forge-std submodule.
- **Ran gitleaks locally on all 37 commits:** no real secrets.
  - The 4 hits were public values: anvil's published dev keys in tests, and Circle's Base Sepolia USDC address. They're allowlisted in `.gitleaks.toml`.
  - In the working tree it flags only `.env` (the real Stripe test keys), which git ignores.
