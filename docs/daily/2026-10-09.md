# 2026-10-09: Pilot shadow mode

## Shipped
- **Shadow mode for pilots** (plan §8, test layer 7), per account: `PUT /v1/ops/accounts/:id/shadow-mode`.
  - Automatic decisions are recorded as usual, but held with `review_pending: true`.
  - They can't settle until a reviewer acts, not even when forced. This is enforced in the pure state machine (new `REVIEW` event and `review_pending` guard on `SETTLE`).
  - **Confirm:** clears the hold and keeps the appeal window.
  - **Override:** writes a `review_override` human decision and restarts the appeal window, so the side that now lost can appeal.
  - A dispute resolution also clears the hold.
  - Every review is a `decision_reviews` row, plus an `agreement.review` ledger entry and webhook.
  - **Ops API:**
    - `POST /v1/ops/agreements/:id/review`.
    - `GET /v1/ops/reviews[/pending|/stats|/golden-candidates]`.
    - The golden-candidates export (NDJSON) labels each disagreement with the reviewer's outcome, for curation into the golden sets.
  - **Dashboard:** held decisions appear in the review queue. The case page has "Confirm the automatic decision" and an override form.
  - **`/accuracy`:** shows how many automatic decisions were human-reviewed. Overrides count as overturns, and the last human word wins.
- **Bug fixed: reviewer payouts ignored the configured rates.** They always paid the USD defaults, even with `REVIEWER_RATE_*` set. They now use the configured rates. Shadow reviews are paid at the decision rate; an override counts once.

# 2026-10-09: Evaluator-for-hire on any ERC-8183 contract (Part 10)

## Shipped
- **Proof Desk can evaluate jobs on other parties' ERC-8183 contracts.** Guide: `docs/integrations/erc8183-evaluator.md`.
  - `GET /v1/agreements/:id/external-job/terms` and `POST /v1/agreements/:id/external-job`.
  - The job is read from the chain and must match the agreement on every point: our evaluator, the exact budget, the token, a description tag binding it to this agreement and spec, enough time before expiry, and no hook.
  - Settlement uses the standard calls: `complete` (only after the provider's `submit`) or `reject`.
  - Expiry reclaims are recorded. Late attachments are refunded straight away.
- **No partial outcomes on these jobs.** The standard can't express them.
  - A verifier's partial proposal escalates to a human.
  - A human partial decision is refused (`422 partial_unsupported`).
- **Public listing:** `/.well-known/erc8183-evaluator.json` (address, chain, verticals, pricing, steps). Any ecosystem or marketplace can read it.
- **`ReferenceERC8183.sol`:** a plain, test-only ERC-8183 implementation. The viem gateway completes and rejects jobs on it on anvil.
- **Fix from shadow mode:** the on-chain settlement reason now covers review overrides (`agreement.review`), so it no longer points at the overridden automatic decision.

# 2026-10-09: Agent card payments (Stripe SPTs) and the large-job limit

## Shipped
- **Shared payment tokens:** MPP/ACP agents can fund a card hold with a Stripe shared payment token: `POST /v1/agreements/:id/card-hold {"shared_payment_token": "spt_…"}`.
  - Before charging, the token is checked: active, unexpired, same currency, limit ≥ the agreement amount. Otherwise `422 shared_payment_token_rejected` with the reasons.
  - Stripe calls for SPTs pin the preview API version `2026-09-30.preview`.
  - Also in the SDK (`createCardHold`) and the MCP `fund_purchase` tool.
  - **Live Stripe test mode passes:** the test helper grants an SPT, it authorizes a $180 manual-capture hold, and the hold is cancelled (`npm run stripe:e2e`).
- **Direct-hold limit:** live jobs over $5,000 (`PRICING.directHoldMaxCents`) can't be funded by card hold, a Proof Desk on-chain job or an external ERC-8183 job (`422 amount_requires_partner`).
  - The plan (§1) routes big-ticket B2B through a licensed escrow partner, and none is integrated yet.
  - Test mode is unrestricted. The pricing page says so.
  - Change the limit only with legal sign-off.

# 2026-10-09: Step 1 of the review plan: the Verify API

## Shipped
- **`POST /v1/verifications`:** checks work against acceptance criteria with no payment held, in live mode too.
  - The job runs as an agreement on a new `none` rail. Creation, approval, the delivery and the verifier run happen in one call.
  - So it gets the ledger, per-check billing, escalation to a human, shadow review and disputes, unchanged.
  - The amount is optional (zero), there's no appeal window unless you ask for one, and the scheduler closes the job without moving money.
- **Outages:** a verifier outage returns the error with `verification_job_id`; `POST /v1/verifications/:id/retry` finishes the job.
- **Also:** `GET /v1/verifications[/:id]`, SDK `pd.verifications.*`, MCP tool `verify_work`, a quickstart section, and the dashboard labels these "verification only".
- **Why:** the review's point that revenue should be verification-fee-first. Checking showed live `verify_only` accounts couldn't verify anything, because a delivery needed a funded hold.
- **Spec change:** amounts may now be zero. Every funding rail (card, Proof Desk on-chain job, external ERC-8183 job) refuses zero (`422 amount_required`).
