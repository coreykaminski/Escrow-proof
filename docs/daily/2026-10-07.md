# 2026-10-07: Part 4 Card rail (Stripe)

**Slice:** Connect Express sellers → card authorization holds → webhooks → settlement (capture / cancel / partial / refund + transfer) → expiry handling → scheduler. Built against a Stripe simulator because no Stripe key yet. Part 3's model eval is still waiting on Anthropic credits.

## Shipped
- `packages/payments`:
  - `PaymentsGateway` interface and `StripeGateway`: Stripe SDK v23, Connect Express accounts, PaymentIntents with `capture_method: manual` and `request_extended_authorization: if_available`, separate charges and transfers, `constructEvent` webhook verification, Stripe errors mapped to retryable/non-retryable.
  - `FakeGateway`: an in-memory Stripe with lapsing authorizations, partial capture, cancel vs refund, transfers that need an onboarded seller, idempotency (same key → same result, different params → error), and signed webhooks.
  - `planSettlement` (pure): plans from the hold's *live* state, so a retry after a partial failure resumes. Fee: 2%, min 50, cap 25,000 minor units.
- API:
  - `POST /v1/sellers/:ref/onboarding`, `GET /v1/sellers/:ref`
  - `POST /v1/agreements/:id/card-hold` (authorizing the card funds the agreement), `GET /v1/agreements/:id/hold`
  - `POST /webhooks/stripe`: signature-checked; each event processed once via `webhook_events`; it always re-reads the payment intent, so out-of-order events are harmless; if processing fails the event is forgotten so Stripe's retry runs it again.
  - Ops `settle` moves card money (eligibility is dry-run first). `POST /v1/ops/run-due` and CLI `run-due`: capture holds near expiry, refund missed deadlines, settle due agreements.
  - Chargebacks are recorded and block payout. A card confirmed after the delivery deadline has its authorization released.
  - Migration `0004_card_rail` (`seller_accounts`, `holds`, `webhook_events`). Core `HoldRail` now includes `card`.
- `npm run stripe:e2e`: real Stripe test-mode checks for hold, idempotent replay, extended auth, full/partial capture, cancel, refund, and optionally a transfer. It refuses non-test keys.

# 2026-10-07 (afternoon): Part 5 Developer surface

**Slice:** outbound webhooks → TypeScript SDK → sandbox test helpers → MCP server → OpenAPI and docs → quickstart.

## Shipped
- **Outbound webhooks**:
  - Platforms register endpoints with `POST /v1/webhook-endpoints`; the secret is shown once.
  - Events are the platform's own ledger entries (`evt_<seq>`, stable ids), delivered in ledger order and signed `Proofdesk-Signature: t=…,v1=HMAC-SHA256`.
  - The cursor advances only on a 2xx response, so delivery is at-least-once and ordered.
  - Exponential backoff: 1 min doubling, capped at 6 h. An endpoint is disabled after 20 failures. Event-type prefix filters. Attempt log.
  - Delivery runs in the scheduler tick (`run-due`).
- **`@proofdesk/sdk`**: no dependencies; typed resources (agreements, sellers, webhook endpoints, test helpers); auto Idempotency-Key reused across retries; typed `ProofDeskError`; `verifyWebhook` (Web Crypto, timestamp tolerance, constant-time compare).
- **Sandbox**: `/v1/test_helpers/agreements/:id/{decide,verify,settle}`, test-mode keys and test agreements only.
- **MCP server** (`apps/mcp`):
  - Tools: `create_protected_purchase` (amounts in major units, optional source document), `approve_purchase_terms`, `fund_purchase`, `get_purchase`, `list_purchases`, `submit_delivery`, `open_dispute`.
  - Sandbox-only: `sandbox_run_verification`, `sandbox_simulate_decision`, `sandbox_settle`.
  - Every response includes a `next_step` for the agent. API errors come back as readable tool errors.
- **OpenAPI 3.1** generated from the same zod validators the routes use, served at `/openapi.json`, with a reference page at `/docs`. A test fails if any served route is undocumented, or a documented one doesn't exist.
- **Quickstart** (`docs/quickstart.md`) and `examples/quickstart.ts`.

# 2026-10-07 (night): Stripe live run on the new account, Connect on

The key was swapped for a new test account (Canada, settles in CAD) and Connect was enabled. All `stripe:e2e` checks now pass live, including the seller payout and seller onboarding. Three real-world issues the simulator couldn't show, all fixed:
1. **Accounts v1 creation is blocked** on new Connect platforms ("Stripe no longer recommends Accounts v1"). Seller accounts now use **Accounts v2** (`dashboard: express`, recipient `stripe_transfers` plus merchant `card_payments`, which Stripe requires for US sellers; the platform collects fees and bears losses). Onboarding links use v2 account links. Seller status is read from the v2 capabilities and requirements.
2. **v2 needs the seller's country and contact email up front.** `POST /v1/sellers/:ref/onboarding` now takes `{email, country}` (country defaults to `us`); the SDK is updated.
3. **Currency:** a USD charge settles in CAD on this platform, and Stripe requires the transfer in the settlement currency. `transfer()` now converts the seller's share at the charge's own rate (balance transaction ÷ amount captured) and returns what was actually paid. The settlement records `seller_paid`. Live: an 18,000-cent USD hold paid out CA$251.51.
