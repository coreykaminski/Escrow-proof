# Security review: October 2026 (Part 9)

Scope: the whole system as of this commit (API, dashboard and public pages, payments on both rails, verifiers, worker). Method: walk each trust boundary, list what an attacker controls, check the controls in code, fix what's missing, and add a test for each fix.

## Who can attack, and what they control

| Actor | Controls | Wants |
|---|---|---|
| **Seller** (or a seller's agent) | Delivered files: text, code, data, reports with links | Get paid for bad work; reach our infrastructure |
| **Buyer** | Spec inputs (sources, tests, schemas), disputes, card disputes | Get work free; refund after accepting |
| **Platform** (API key holder) | Agreements on its own account, webhook URLs, share links | Read other platforms' data; make us call internal hosts |
| **Anyone on the internet** | Public pages: share links, payment pages, x402, login, status | Guess tokens, brute-force keys, overload us |
| **Insider / leaked key** | An ops key | Decide cases, pay themselves |

## Controls by boundary

**Authentication and isolation**
- API keys: 192-bit random, stored only as sha256, scoped (`platform` / `ops`), test vs live mode enforced on every money path.
- Every query is scoped by account; cross-account access returns 404, and tests cover it.
- Dashboard sessions are HttpOnly, SameSite=Lax, and **Secure behind the TLS proxy** (fixed here). Session ids are stored hashed, last 12 h, and end when the key is revoked. Every form carries a CSRF token.
- Share and payment links: 192-bit tokens, stored hashed, expiring, revocable. Reports never include documents.

**Untrusted deliverables**
- Translation and data are always treated as data. Prompts wrap them as untrusted.
- Injection phrases are scanned **after Unicode normalization** (fixed here: zero-width, full-width, bidi, look-alike letters).
- Any model quote used as evidence must appear in the texts.
- **Code** is the riskiest input:
  - The sandbox runs with no network, an unprivileged user, a read-only root, no capabilities, and memory/CPU/PID limits.
  - Tests come from the buyer and always win over the delivery.
  - A static scan flags network, process, env and eval APIs the task doesn't need.
  - **Fixed here:** results were read from the test reporter's output in the same process as the delivered code, which could monkeypatch `assert` or forge output. A trusted runner now loads first, takes a one-time key the code can't read, freezes assertions and locks the stream and event methods, and signs the results. Only the signed line counts.
  - **Fixed here:** a sandbox outage used to look like "tests didn't run" and refund the buyer. It is now a retryable 503.
- **Research citations** are fetched through an SSRF guard. Every resolved IP is checked at connect time: no private, loopback, link-local or metadata addresses, which also defeats DNS rebinding. Redirects are re-checked and responses are bounded.

**Outbound calls we make for customers**
- **Fixed here:** webhook URLs could be `http://localhost` and deliveries went to any address. In production, endpoints must be public https on standard ports, and every delivery goes through the same connect-time guard, with no redirects.

**Money**
- No custody: card authorizations stay with Stripe; USDC stays in a public contract where Proof Desk is only the evaluator.
- Every money movement has a stable idempotency key; settlement is planned from the processor's live state; webhooks are signature-checked and processed once.
- Contract: only the evaluator decides, it can't pay the seller after expiry, an expired job is always refundable by anyone, the fee is capped at 5% and locked per job. These are checked by Foundry invariants, and a planted bug was caught.
- Fees: verification and dispute fees are written in the same transaction as the event they bill for, deduplicated by reference. Only live-mode usage is invoiced.

**Web surface**
- **Added here:**
  - CSP on every HTML page (no inline script; Stripe.js is the only third-party script on the card page).
  - `Referrer-Policy: no-referrer` (link tokens are in URLs), `nosniff`, frame denial, HSTS behind TLS, `no-store` on pages.
  - The API reference loads Scalar **pinned to an exact version with Subresource Integrity**, under its own CSP. It previously loaded the unpinned latest version.
- **Added here:** body-size limits (API 24 MB, dashboard 256 KB, pay pages 64 KB, Stripe webhooks 1 MB).
- **Added here:** rate limits, which answer 429 with `Retry-After`:
  - 600 requests/min per API key;
  - 10 sign-in attempts per 15 minutes per IP;
  - 120 requests/min per IP on share and payment links.
- Errors never include stack traces or internal messages (500s are logged and answered generically).

**Integrity and audit**
- Hash-chained, append-only ledger. UPDATE and DELETE are blocked by database triggers.
- The worker re-verifies the whole chain every 6 hours and shows the result on `/status`.
- On-chain settlements carry the decision's ledger hash.

## Findings fixed in this review

| # | Severity | Finding | Fix | Test |
|---|---|---|---|---|
| 1 | Critical | Delivered code could fake passing tests (monkeypatch `assert`, forge or silence reporter output) | Trusted signed runner, frozen assertions, locked stream/event methods | `code.test.ts` "red team…" (6 attacks), golden `patched_assert` / `forged_results` (20 items) |
| 2 | High | A sandbox outage was treated as failing tests, so buyers got refunded on our infra failure | `SandboxUnavailableError` → 503, agreement stays in `verifying` | `code.test.ts` "an unavailable docker…" |
| 3 | High | Webhook endpoints could target localhost, private or metadata addresses (SSRF) | Public-https rule in production; connect-time IP guard on every delivery | `security.test.ts` "outbound webhooks…" |
| 4 | Medium | Injection phrases could be hidden with zero-width, full-width or look-alike characters | `normalizeForScan` before every injection scan | `code.test.ts` "hiding injection text" |
| 5 | Medium | The API reference loaded an unpinned third-party script on the dashboard's origin | Exact version + SRI + its own CSP | `security.test.ts` |
| 6 | Medium | No rate limits: key brute force, sign-in brute force, link-token guessing, cost abuse | Fixed-window limits per key and per IP | `security.test.ts` "rate limits" |
| 7 | Medium | The session cookie wasn't `Secure` behind Fly's TLS proxy | Secure when the original request was https | `security.test.ts` "dashboard cookie" |
| 8 | Low | No security headers; share-link tokens could leak via `Referer` | Header middleware, `no-referrer` | `security.test.ts` "security headers" |
| 9 | Low | No request body limits | `bodyLimit` per surface | `security.test.ts` "request size" |

## Open items (not fixed yet)

- **Rate-limit store is per process.** That's fine for one web machine; with more, move to Postgres or Redis (`RateLimitStore` interface).
- **Python code verification:** the runner signs results, but Python classes can't be frozen, so a determined delivery could still patch `unittest` assertions. Mitigations: hidden tests, the model judge, human escalation. Prefer Node test suites until this is redesigned (assertions evaluated out of process).
- **Node's permission model is not a security boundary.** Production must use the Docker sandbox (with gVisor) on a separate host; `CODE_SANDBOX=node` is for development and CI only.
- **Secrets:** the evaluator key and Stripe keys are environment variables. Before mainnet or live money, move the evaluator key to a KMS/HSM signer and contract ownership to a multisig.
- **External contract audit** before Base mainnet (plan Part 7).
- **Dependencies:** `npm audit --omit=dev` finds nothing. The full audit reports 4 moderate advisories, all in esbuild bundled inside `drizzle-kit`, a dev-only migration generator. The advisory concerns esbuild's dev server, which we never run. Still to do: remove dev tools from the production image (precompile instead of running `tsx`), add Dependabot, and run a weekly audit in CI.
- **Pen test** by a third party before design-partner go-live with real money.
